# Design — hitorro-mesh-datasets

The full version of the "why this exists" story. The README is the elevator
pitch; this file is the longer argument.

## The core insight

Hitorro Mesh already has:

- a **Calcite planner** for SQL over JVS documents,
- a **distributed execution** model with partitioned + broadcast tables,
- a **streaming iterator** that keeps records flowing without materialisation,
- a **BaseFile** abstraction that hides HTTP / S3 / HDFS / local behind one API,
- a **multilingual field** machinery that already models per-language strings,
- a **projection framework** for typed field derivation.

Given all that, the missing piece to build something meaningfully more useful
than YQL 1.0 is not another query engine — it is **a discoverable catalog of
public datasets, with explicit cross-dataset relationships**, so that the
planner can reason about *semantic* joins rather than syntactic ones.

## Guiding principles

1. **Manifest is the thing people publish.** A single YAML file is enough to
   install, register, query, and reason about a dataset. Everything else
   (install scripts, JVS types, register-with-mesh calls) is derived from it.

2. **Preserve the native record.** The system's job is to add structure, not
   overwrite it. Every normalised record carries the source record verbatim
   under `native`, so a schema evolution never forces a re-download.

3. **Identifiers are first-class.** A field isn't just `type: core_string`; it
   also has a `role` like `id.wikidata` or `id.geonames`. The planner uses that
   to plan joins that would otherwise require humans reading three READMEs.

4. **License isn't a string.** ODbL and CC-BY interact in ways that a bare
   SPDX field cannot express. `License` records the five capabilities
   (commercial, redistribute, attribute, share-alike, modify) and
   `LicenseAlgebra.combine` answers "*can this query's result be redistributed
   and under what terms?*" before the query runs.

5. **Three layers, lazy by default.** RAW is source-faithful and immutable.
   NORMALIZED wears the common envelope + canonical identifiers. DERIVED
   (joins, enrichments) is generated by the streaming runtime and only
   materialised for hot queries.

## The four kinds of join

The taxonomy that the roadmap's `USING PLACE` / `USING ENTITY` extensions
resolve against:

- **`EXACT_ID`** — Two datasets carry the same identifier value in the same
  namespace. City has `country_code`, country-info has `iso` — both `role:
  id.iso3166alpha2`. Direct equi-join.

- **`HIERARCHICAL`** — Parent/child in a well-known containment tree. City →
  county → state → country. The planner walks the hierarchy table.

- **`SPATIAL`** — A geometry predicate: `within`, `nearest`, `intersects`,
  `distance-lt`. The relationship parameters carry the predicate;
  execution requires a spatial index (JTS + R-tree, or S2 cells) on the
  agent that holds the polygon-shaped side.

- **`PROBABILISTIC`** — Entity resolution with a `confidence` and `evidence`
  attached. Never presented as truth. The confidence lives on the joined
  row so `WHERE CONFIDENCE > 0.95` is a real filter.

## Why this is different from YQL

YQL was *"SQL over the web"* — a single query language front-ending many APIs
via per-source adapters. Its ceiling was:

1. Every adapter was hand-written.
2. Cross-source joins were ad-hoc — you had to know each API's identifiers.
3. Nothing modelled license semantics.
4. Nothing modelled uncertainty or provenance.

This module's ceiling is:

1. Every dataset is described by a manifest. Adding one is filling in a form.
2. Cross-dataset joins go through declared identifier namespaces or spatial
   predicates. The planner walks the graph.
3. License algebra is a first-class output of every query.
4. Provenance is on every record. Probabilistic joins are labelled as such.

## What lives where

```
Manifest              — the declaration
LicenseAlgebra        — reasoning about combined terms
DatasetRegistry       — in-process catalog + identifier lookup
MeshRegistrar         — announces installed datasets to a running driver
RecordEnvelope        — the wrapper every normalised record wears
Install scripts       — materialise raw → NDJSON + JVS type
```

## What deliberately isn't here (yet)

- **`USING PLACE` / `USING ENTITY` planner rules.** The metadata is ready; the
  jvssql planner extension is the next milestone.
- **Spatial index at the agent.** Needed the moment any polygon dataset lands.
- **License-aware result envelope.** The driver's query response should carry
  the combined `LicenseAlgebra.Result` so consumers can honour it — designed,
  not wired.
- **Auto-registration Spring module.** A tiny Spring Boot autoconfigure that
  loads bundled manifests and registers anything installed on disk. Straight-
  forward; deferred so this module stays framework-neutral.

## What deliberately isn't here (ever)

- **Any warehouse-style materialised universal table.** The whole point is
  that datasets stay separate, joinable by declared relationships, with
  licences preserved. Fusing them into a single normalised table erases the
  provenance and the license algebra along with it.

- **A shared "clean" schema everyone must conform to.** The envelope holds
  what the planner needs (`@id`, `@type`, `links`, `geometry`). Native fields
  live alongside. Normalisation is additive, never destructive.
